# 文案到 Remotion 单条/批量统一生产设计

**日期：** 2026-08-18
**状态：** 用户已确认设计，待实施计划
**适用产品：** 上谷 S5Max

## 1. 目标

项目对用户只提供一个生产入口：用户提交未经分类的原始文案，并选择单条或批量。Codex 在内部完成文案拆分、分类、组合、SMB 素材选择、本地 IndexTTS 2.5 逐句配音、Remotion 渲染和成品质检，最终交付 MP4。

合并后的系统必须同时保留：

- 现有单条生产内核的逐句音画时钟、Remotion 唯一编码和严格 QC。
- 现有每日批量层的组合规划、TTS 预热、并发、断点续跑和单条重试。
- 单条模式随机组合一条视频；批量模式默认生产 300 条有意义且不重复的视频。
- 文案组合与完整素材序列在所有历史成片中分别唯一。

## 2. 明确不做

- 不要求用户手工填写分类 CSV、素材矩阵或 ProductionPlan。
- 不新增第二套 TTS、代理、Remotion 渲染或 QC 实现。
- 不使用网络 TTS、网络素材或静默回退；素材只来自本地 SMB。
- 不新增网页、数据库、上传、投放或发布系统。
- 不虚构产品参数、效果、价格、优惠、赠品或保障。
- 不靠改文件名、编码参数、画面焦点或微小时间偏移制造“唯一”视频。
- 不迁移或删除现有产物；旧批次继续作为历史证据保留。

## 3. 用户合同

### 3.1 输入

用户只需提供：

1. 原始文案，可以是直接粘贴的文本或本地文本文件。
2. 模式：`单条` 或 `批量`；未指定时默认单条。

单条模式固定产出 1 条。批量模式默认目标为 300 条，但在昂贵生产开始前先报告最大有效容量、预计耗时和预计磁盘空间，由用户确认最终数量。

### 3.2 系统可以做的文案处理

Codex 可以：

- 拆句并在内部分类为 hook、卖点、场景和 CTA。
- 删除完全重复的句子。
- 调整句子顺序。
- 统一空白和标点。
- 删除相邻句中不影响完整语义的重复主语或产品名。
- 添加少量不包含产品事实的连接词。

Codex 不得新增或改变数字、产品名、功能名、效果结论、价格及成交条件。每个内部句子都必须保留原文、规范化文本和稳定来源 ID，保证可追溯。

若缺少 hook、CTA 或足够的卖点/场景多样性，预检必须指出具体缺口，不得自行编造。

### 3.3 每条视频的文案结构

默认结构为：

```text
1 句 hook + 2 至 4 句不同类别的卖点或场景 + 1 句 CTA
```

同一条视频中不得重复原句或卖点类别。单条模式从合法候选中随机选择一套；批量模式从合法候选中选择目标数量的唯一组合。

## 4. 总体架构

### 4.1 唯一用户入口

`skills/auto-edit-product-video` 是唯一对外工作流。用户不直接操作内部 CSV、JSON 或脚本参数。

### 4.2 文案准备层

Codex 将原始文案转换为内部句子池。分类 CSV 可以继续作为内部交换格式和测试 fixture，但不再是用户合同。

### 4.3 组合与批量协调层

`scripts/s5max-daily.py` 继续承担：

- 单条和批量的文案组合。
- 历史唯一性检查与批次签名预留。
- 素材容量评估与 SMB 扩展。
- 批次状态、样片闸门、TTS 预热、并发和续跑。
- 对 `scripts/produce.mjs` 的逐条调用。

它不得复制代理、TTS、Remotion 或 QC 实现。

### 4.4 单条生产内核

`scripts/produce.mjs` 保持一条视频的唯一生产内核，负责：

- 校验 ProductionPlan。
- 生成并复用素材代理。
- 调用本地 IndexTTS 2.5 内容缓存。
- 生成逐句 Remotion Props。
- 仅通过 `ProductMarketingProduction` Composition 编码最终 MP4。
- 执行媒体和音量 QC，并原子发布成片与 manifest。

单条与批量不得使用不同的成片标准。

## 5. 模式与数据流

### 5.1 单条模式

```text
原始文案
→ 自动拆句与分类
→ 排除历史组合后随机选择一套合法文案
→ 本地逐句 TTS
→ 按真实 WAV 时长匹配 SMB 镜头
→ ProductionPlan
→ produce.mjs
→ Remotion + QC
→ 交付 1 个 MP4
→ 登记历史签名
```

单条模式不需要容量确认或样片闸门；生成的这一条就是正式交付。用户需要另一种组合时，创建新批次。

### 5.2 批量模式预检

在生成语音或视频前，协调层读取：

- 规范化句子池。
- 已完成与已预留批次的签名。
- 当前已视觉验证的 SMB 素材目录。
- 可继续扫描的 SMB 本地路径。

预检报告：

- 最大有效唯一容量。
- 默认建议数量 300。
- 预计 TTS、代理、渲染时间和磁盘空间。
- 阻止达到 300 的文案或素材类别缺口。

用户确认数量后才进入昂贵阶段。

### 5.3 批次创建与封存

每个批次生成唯一 `batchId` 和一次性随机种子。随机结果只在创建时产生，随后固定；重试、重启和续跑不得重新洗牌。

确认数量后：

1. 生成目标数量的文案组合。
2. IndexTTS 2.5 单次加载，预热本批次全部不同句子的内容缓存。
3. 使用真实 WAV 时长选择能覆盖完整语音的语义匹配镜头。
4. 生成所有 ProductionPlan。
5. 验证文案、素材、文件和历史唯一性。
6. 原子封存 manifest 并预留签名。

封存后不得静默改变文案或镜头。需要改变时必须废弃该批次并创建新批次。

### 5.4 单样片闸门

协调层从封存批次中选择一条结构和时长具有代表性的计划并渲染。该样片属于目标数量的一部分。

- 用户批准：批次进入 `sample_approved`，样片计入最终数量，续跑其余 `targetCount - 1` 条；默认批次即续跑 299 条。
- 用户拒绝：整个批次进入 `archived`，归档样片和诊断，释放其预留签名；根据反馈创建新批次和新样片。

只修改样片而保留其余未验证计划是不允许的。

### 5.5 批量生产

样片批准后，协调层以受控并发调用同一个 `produce.mjs`。每条视频独立推进状态，失败项不阻止其他条目完成。已经验证的音频、代理和 MP4 不重复生成。

## 6. SMB 素材策略

素材选择顺序为：

1. 复用现有已视觉验证的 SMB 素材及代理。
2. 如果有效唯一容量不足 300，自动扫描 SMB 中尚未入库的素材。
3. 为新素材建立本地代理、元数据和视觉核验记录。
4. 只把语义、画面质量和时长均合格的镜头加入候选池。

优先级固定为：

```text
文案与画面语义对应 > 有意义的唯一性 > 素材使用均衡 > 数量
```

系统必须主动扩展合格素材以达到 300；但扫描后仍无合格镜头时，应报告真实缺口，不得用不相关画面凑数。

一个镜头的身份由视觉核验后登记的实际内容片段决定。同一源文件中内容确实不同的独立片段可以登记为不同镜头；仅改变文件名、编码、裁切位置、焦点或偏移少量帧不产生新镜头。

## 7. 唯一性与历史范围

唯一性覆盖所有历史正式成片和当前已封存批次的预留签名。

### 7.1 文案签名

文案签名同时包含：

- 有序的来源句子 ID。
- 规范化后的最终字幕文本。

仅改变标点、空格或连接词不算新文案。改变合法句子选择或形成不同有效叙事顺序可以算新组合。

### 7.2 画面签名

画面签名由有序镜头身份组成。每条成片的完整镜头序列必须在历史和当前批次中唯一。

### 7.3 登记与预留

不新增数据库。历史来源为本地 manifest：

- 批次封存时使用短时原子锁读取历史并预留签名。
- 其他并发 Session 规划时同时避开永久和预留签名。
- 样片拒绝或批次取消时释放预留。
- 整批完成后将预留转换为永久历史记录。

未通过 QC、未交付或已归档的样片不进入永久历史。

## 8. 逐句 TTS 与 Remotion 时钟

每个计划句子对应：

- 一份本地 IndexTTS 2.5 WAV。
- 一个字幕区间。
- 一个语义匹配镜头区间。
- 一个连续的 Remotion Sequence。

时钟合同固定为：

- 30 fps。
- `voiceFrames = ceil(wavDurationSeconds × 30)`，最少 1 帧。
- 非末句 `pauseFrames = 5`；末句为 0。
- 下一句从前一句 `voiceFrames + pauseFrames` 后开始。
- 字幕只覆盖 `voiceFrames`，停顿期间不可见。
- 镜头源区间必须至少覆盖完整 `voiceFrames`。
- 停顿期间允许冻结该句最后一帧，但语音期间不得靠冻结补足素材。
- 音频不得截断、拉伸或使用静音替代。

TTS 缓存键必须包含引擎版本、语言、配置、音色哈希、规范化文本和时长因子。一次预热调用最多加载一次模型，损坏或截断的 WAV 必须单句重生。

## 9. 状态与续跑

批次状态：

```text
draft
→ capacity_confirmed
→ audio_ready
→ sealed
→ sample_pending
→ sample_approved
→ rendering
→ complete
```

拒绝或取消的批次进入 `archived`。

条目状态：

```text
planned → voiced → rendered → verified
```

每次状态变化必须原子写入 manifest。程序退出或机器重启后从 manifest 继续，不得重新组合或覆盖已验证成片。

## 10. 失败处理

- 输入、必要分类、组合容量或本地路径错误：在昂贵阶段前拒绝。
- TTS 预热失败：不封存批次，只重试失败句子；禁止切换网络 TTS。
- SMB 不可用：保留状态等待恢复；禁止远端素材回退。
- 精确 WAV 时长找不到合格镜头：扩展同类 SMB 素材；仍失败则报告具体句子与类别。
- 单条生产失败：记录错误并继续其他条目。
- QC 失败：保留诊断和 partial 产物，不发布正式 MP4，不登记永久签名。
- 输入文案改变：创建新批次，不修改已封存批次。
- 正式输出发布使用临时文件和原子改名，避免半成品占用正式文件名。

## 11. 输出与保留策略

新批次使用统一目录，不覆盖现有单条或每日样片产物：

```text
work/production-batches/<batchId>/
├── source-copy.txt
├── copy-pool.json
├── manifest.json
├── plans/
├── qc/
└── retries/

out/production-batches/<batchId>/
├── <videoId>.mp4
└── ...
```

`work/production/<videoId>/` 继续由单条生产内核保存 props、代理链接、TTS manifest、联系表和最终 manifest。

用户主要接收正式 MP4 目录和简短汇总；内部文案池、计划、缓存、签名、QC 和重试记录全部保留以支持审计与续跑。

## 12. 验收标准

### 12.1 单条模式

- 未指定模式时默认单条。
- 从用户文案中随机选择一套合法结构并锁定。
- 生成 1 个通过全部媒体 QC 的 MP4。
- 文案和画面签名未出现在永久或预留历史中。
- 完成后签名进入永久历史。

### 12.2 批量模式

- 预检在昂贵阶段前报告容量、时间、空间和缺口。
- 默认目标为 300，最终数量由用户确认。
- `targetCount` 个文案签名唯一且避开历史；默认批次为 300 个。
- `targetCount` 个画面签名唯一且避开历史；默认批次为 300 个。
- 每条符合 `1 hook + 2–4 卖点/场景 + 1 CTA`。
- 同条内部无重复原句、卖点类别或镜头身份。
- 批次创建后重跑得到相同 manifest。
- 先只渲染 1 条代表性样片。
- 样片拒绝会归档整批并释放预留；批准后只生产剩余条目。
- 最终 `targetCount/targetCount` 为 `verified` 才能进入 `complete`；默认批次即 300/300。

### 12.3 每条成片

- 文案只来自用户输入，允许的轻量处理没有改变事实。
- 每句具备有效本地 WAV、同步字幕和语义对应镜头。
- 逐句帧时钟连续，非末句恰好 5 帧停顿。
- 语音不截断，字幕不覆盖停顿，素材覆盖语音时长。
- 只有 `ProductMarketingProduction` Remotion Composition 编码最终 MP4。
- 视频为 H.264、1080×1920、30 fps、yuv420p。
- 音频为可听的 AAC 单声道。
- 容器可完整解码，manifest 中的文件、哈希、时长和帧数与成片一致。
- 最终路径及生产计划不包含 URL 或远程依赖。

## 13. 必要测试

实现至少覆盖：

1. 原始文案到内部句子池的来源追溯和禁止新增事实。
2. 单条随机一次后可续跑，新批次产生新候选。
3. 批量 300 条结构、文案签名和画面签名唯一。
4. 跨历史与并发预留的重复拒绝及归档释放。
5. 容量不足时先扩展 SMB，仍不足时给出精确缺口。
6. 真实 TTS 时长下的镜头覆盖和 5 帧停顿。
7. 样片批准、拒绝和整批重建。
8. TTS 单次加载、内容缓存、损坏 WAV 单句重生。
9. 单条失败后其他条目继续，重跑只处理未完成项。
10. 1 条真实单条端到端成片通过 QC。
11. 1 条真实批量样片通过人工闸门流程。
12. 300 条 dry-run 通过全部合同检查。
13. 300 个正式 MP4 全部通过媒体 QC 后整批才完成。

## 14. 合并完成条件

以下条件全部满足才视为合并完成：

1. 用户只提供原始文案和模式，不再准备分类 CSV 或计划 JSON。
2. 单条与批量都通过同一个协调层和同一个单条生产内核。
3. 不存在第二套 TTS、代理、Remotion 或 QC 路径。
4. 单条模式能直接交付 1 个唯一成片。
5. 批量模式能完成单样片批准流程，并续跑至 `targetCount/targetCount`；默认 300 条能力必须通过验证。
6. 文案与画面唯一性跨所有历史正式成片生效。
7. SMB、本地 IndexTTS 2.5、逐句时钟、Remotion 唯一编码和 QC 合同全部保持。
8. 现有产物保留，旧入口不再作为用户可见的平行工作流。
